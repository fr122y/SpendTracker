# Design

## Context

См. мотивацию и пользовательский результат в `proposal.md`, а проверяемые контракты — в `specs/pockets/spec.md`. Dashboard уже передаёт общий `selectedDate`; расходы и project movements хранятся в DB и читаются через Server Actions. Аналитика включает записи типа `expense`, а личное weekly coverage исключает project-linked расходы и покрывается проектными снятиями.

## Goals / Non-Goals

**Goals:** сохранять историю под устойчивым ID кармана, инициализировать месячные бюджеты без перезаписи существующих периодов, использовать общий защищённый поток операций расходов и обеспечить расчёт недельного покрытия для переводов.

**Non-Goals:** отдельный календарь, остатки/пополнения как банковские деньги, перенос неиспользованных средств, отдельная запись возврата и изменения shared-budget поведения.

## Decisions

### Хранить карманы и бюджеты отдельными сущностями

Добавить `pocket` с владельцем `userId`, именем и `archivedAt`, а месячные бюджеты хранить отдельно с периодом `YYYY-MM` и уникальностью по `(pocketId, period)`. Не хранить `used` или `remaining`: обе величины вычисляются из операций выбранного периода, а остаток может быть отрицательным. Это предотвращает изменение исторического бюджета при редактировании соседнего месяца и сохраняет историю после переименования.

При первой инициализации активного кармана в месяце брать сохранённый бюджет из максимального периода, строго меньшего выбранного; если подходящего периода нет — ноль. Создание периода выполняется в транзакции, синхронизированной блокировкой строки кармана, с уникальным ограничением периода и повторным чтением сохранённой строки. Это защищает от двух одновременных запросов. Инициализация не переносит остаток и не использует будущие периоды. Для архивного кармана отсутствующий период не создаётся; существующие периоды остаются доступны.

### Расширить общую операцию расхода

Использовать существующую `expense` запись для покупки и перевода, добавив nullable `pocketId` и отдельный тип `pocket_transfer`. Покупка остаётся `operationType: expense`, сохраняет категорию/дату/комментарий и потому автоматически остаётся в текущей месячной аналитике. Перевод — не expense и не попадает в суммы/категории расходов. Это повторно использует существующие списки и редактирование операций, вместо параллельного нестыкующегося журнала.

Server Actions должны разрешать операции с `pocketId` только владельцу активного кармана, проверять сочетания полей и не смешивать pocket, project и shared-budget scopes. Для личного weekly spend селектор должен исключать pocket-linked покупки так же, как он исключает project expenses. Для покрытия перерасхода группировать переводы по карману за неделю и применять к ним те же ограничения и хронологическое распределение покрытия, что и к проектным снятиям. Коррекция возврата изменяет сумму перевода; новая операция возврата не добавляется. Суммы остаются в рублях и используют тот же числовой формат, что и текущий `Expense` контракт.

Рассматривалась отдельная таблица pocket operations. Она дала бы более узкую схему, но потребовала бы второго авторизованного потока, отдельного редактирования и загрузки данных для истории и weekly coverage. Использование общей операции уменьшает дублирование и сохраняет действующий разбор расходных итогов по `operationType`; цена решения — новые проверки, исключающие несовместимые сочетания `projectId`, `sharedBudgetId` и `pocketId`.

### Подключить существующий dashboard и историю

Реализовать entity и management feature в существующих FSD слоях; асинхронные данные читать и изменять через TanStack Query и авторизованные Server Actions с optimistic update, rollback и refetch. Повторно используемый `useCategorize` находится в публичном API category entity: покупки карманов и обычные расходы применяют один matcher, а ручной выбор категории сохраняет keyword mapping для будущих операций. Виджет получает `selectedDate` из session store, а формы новой операции используют его как дату по умолчанию; при редактировании записи дата и остальные разрешённые поля изменяемы. Добавить виджет в `WidgetId`, registry и нормализованный layout: действующий `getLayoutConfig` добавляет отсутствующие виджеты в устаревшие сохранённые конфигурации. Новый slice получает README.

Архивированный карман остаётся доступен для периодов, в которых уже сохранены данные; бюджет и суммы операций этих периодов редактируемы, комментарий, дата и категория показаны только для просмотра. История использует одну общую `ExpenseCard` на операцию и существующий `useDeleteExpense`: сумма редактируется так же, как в журнале, а удаление требует подтверждения и сохраняет optimistic rollback. Явное удаление пользователем доступно и в архивной истории; остальные бюджеты и операции при этом сохраняются. Новые периоды и операции после архивации запрещены. Переименование меняет отображаемое имя кармана, а связанные записи остаются прикреплены по ID.

## Risks / Trade-offs

- **Новая разновидность операции может попасть в расходные или проектные расчёты по умолчанию →** явно классифицировать её во всех selectors и Server Actions; покрыть regression tests для месячных итогов, личного weekly spend, истории проектов и переводов.
- **Два запроса могут инициализировать один период одновременно →** уникальный ключ `(pocketId, period)`, транзакционная синхронизация на записи кармана и чтение итоговой сохранённой строки.
- **История показывает операцию с датой вне открытого периода после её редактирования →** обновлять запросы после мутации и определять месяц/неделю по сохранённой дате, не по исходному экрану.
- **Архивация не должна разрушать ссылки и историю →** soft archive без автоматического удаления кармана, месячных бюджетов или операций; пользователь удаляет отдельную запись только явно и через подтверждение. Запрет создавать новые записи проверяется сервером.

## Migration Plan

Сгенерировать Drizzle migration как reviewable repository artifact вместе с обновлением schema; в рамках T-027 не применять её к production или другой реальной базе. Сначала внедрить schema/API и selectors, затем entity/UI и интеграционные проверки. Откат релиза выполняется через возврат кода; новые таблицы/поля остаются неиспользуемыми. Удаление данных или обратную destructive migration не выполнять.
