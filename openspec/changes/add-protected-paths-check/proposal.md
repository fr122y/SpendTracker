# Proposal

## Why

Файлы, которые определяют проверки репозитория (CI workflow, хуки, конфигурация lint, типов, тестов, commit-сообщений и OpenSpec), сейчас защищены только правилом в `docs/engineering/protected-operations.md`. Pull Request может ослабить или отключить проверку тем же изменением, которое она должна была остановить, и остаться зелёным. Из последних 30 слитых Pull Request определения проверок затронули 7: 6 процессных и 1 продуктовый.

## What Changes

- Добавить workflow `.github/workflows/protected-paths.yml` с одним job `protected-paths` на событии `pull_request_target`: workflow, скрипт и список путей берутся из базовой ветки, поэтому Pull Request не может изменить проверку, которая его оценивает. Код из head Pull Request не извлекается и не исполняется.
- Добавить список `.github/protected-paths.txt` (по одному glob на строку) и скрипт без зависимостей `.github/scripts/protected-paths.mjs`, который получает изменённые файлы Pull Request через REST API, учитывает оба имени при переименовании и завершает job с ошибкой при совпадении со списком.
- `package.json` обрабатывается отдельно: он считается защищённым только при изменении значений `scripts` или `lint-staged`; изменение одних зависимостей проходит. Удалённый или неразбираемый `package.json` считается защищённым.
- Проверка закрывается в безопасную сторону: при ошибке API или неполном списке файлов job падает.
- Добавить unit-тесты чистых функций скрипта в `.github/scripts/protected-paths.test.mjs`; workflow запускает их перед самой проверкой.
- Дополнить раздел «Checks» в `docs/engineering/protected-operations.md` описанием проверки и порядка слияния.

Критерии приёмки: unit-тесты скрипта проходят; локальный запуск скрипта в режиме чтения на реальных Pull Request #44, #41, #38 и #29 даёт ожидаемый результат (совпадения в #44 и #38, включая `scripts` в `package.json`; отсутствие совпадений в #41 и #29); на Pull Request этого изменения завершаются `commitlint` и `verify`.

Вне рамок: включение `protected-paths` в обязательные status checks и любые настройки репозитория и ruleset (отдельный шаг владельца после слияния); защита критичных зон приложения (auth, база данных, деплой) и файлов инструкций агентов (`AGENTS.md`, `.claude/`, `.agents/`) — критичные зоны затронуты в 13 из 30 последних Pull Request, блокировка сделала бы обход рутиной; механизм одобрения внутри проверки (метки, комментарии); изменение существующих workflow, кода приложения и тестов.

Зависимости: встроенные `fetch` и `node:test` из Node 22, автоматический `GITHUB_TOKEN` с правами `contents: read` и `pull-requests: read`; новых npm-зависимостей и секретов нет.

Риски:

- На Pull Request этого изменения новая проверка не запускается: `pull_request_target` использует workflow базовой ветки, где файла ещё нет. Поведение подтверждается unit-тестами и локальными запусками на реальных Pull Request.
- Безопасность `pull_request_target` держится на том, что workflow никогда не извлекает и не исполняет код из head. Любое будущее изменение workflow обязано сохранить это свойство.
- Проверка не останавливает агента с правами администратора: обход ruleset доступен ему так же, как владельцу. Проверка создаёт осознанное трение, а не техническую границу.
- Легитимное изменение определений проверок теперь всегда красное и сливается владельцем через обход ruleset `Protect main` после подтверждения зелёного `verify`.
- Имя проверки `protected-paths` позже станет обязательным status check, поэтому переименование job после этого потребует синхронного изменения настроек репозитория.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None. Наблюдаемое поведение приложения не меняется, поэтому изменение объявлено с `skip_specs: true` без spec delta.

## Impact

Затрагиваются только CI-конфигурация (`.github/workflows/protected-paths.yml`, `.github/protected-paths.txt`, `.github/scripts/`) и один абзац в `docs/engineering/protected-operations.md`. Код приложения, существующие тесты и workflow, схема базы данных, зависимости, секреты и настройки репозитория не меняются. Документ `design.md` не создаётся: решения по составу списка, механизму одобрения и событию запуска приняты владельцем и изложены выше.
