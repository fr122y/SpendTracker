# Proposal

## Why

Проверка `verify` показывает, что тесты проходят, но не показывает, что их стало меньше. Pull Request может удалить тестовый файл, пометить тест как `.skip` или убрать тест-кейсы тем же изменением, которое эти тесты ломает, и остаться зелёным. Из последних 30 слитых Pull Request существующие тесты изменялись в 17 (57%) и не удалялись ни в одном: изменение тестов — норма, поэтому проверка должна ловить только ослабление.

## What Changes

- Добавить в workflow `.github/workflows/protected-paths.yml` второй job `test-integrity` на том же событии `pull_request_target`: workflow и скрипт берутся из базовой ветки, код из head Pull Request не извлекается и не исполняется, списки и содержимое файлов читаются только через REST API.
- Добавить скрипт без зависимостей `.github/scripts/test-integrity.mjs`. Тестовым считается файл, путь которого совпадает с `**/__tests__/**`, `**/*.test.ts`, `**/*.test.tsx` или `e2e/**/*.spec.ts`.
- Правило 1, удаление: тестовый файл со статусом `removed` проваливает проверку. Переименование не считается удалением и оценивается по правилам 2 и 3 (прежнее имя на базе против нового имени в head); переименование в путь, который перестал быть тестовым, считается удалением.
- Правило 2, маркеры: для каждого изменённого тестового файла считается число маркеров `.skip(`, `.only(`, `.todo(`, `.failing(`, `xit(`, `xtest(`, `xdescribe(`, `fit(`, `fdescribe(` на базе и в head; проверка падает, если в head их больше. Существующие маркеры сами по себе проверку не роняют; новый тестовый файл с маркером роняет.
- Правило 3, число тест-кейсов: для изменённых и переименованных тестовых файлов статически считаются вызовы `it(` и `test(` с вариантами `.each` и `.concurrent`, без форм из правила 2. Проверка падает, если сумма по всем изменённым существовавшим файлам в head меньше, чем на базе; новые тестовые файлы уменьшение не компенсируют.
- Содержимое «до» читается на merge base: именно относительно него GitHub строит список файлов Pull Request, иначе тест, добавленный в `main` после создания ветки, выглядел бы как удалённый.
- Проверка закрывается в безопасную сторону: неполный список файлов, ошибка API, сдвинувшийся head или тестовый файл, который не удалось получить или декодировать, завершают job с ошибкой.
- Изменить в существующем job `protected-paths` одну строку: шаг unit-тестов запускает только `protected-paths.test.mjs`, чтобы каждый job проверял свой скрипт.
- Добавить unit-тесты `.github/scripts/test-integrity.test.mjs`; job запускает их перед самой проверкой.
- Дополнить раздел «Checks» в `docs/engineering/protected-operations.md` и раздел «Testing Rules» в `docs/engineering/agent-workflow.md`.

Критерии приёмки: unit-тесты обоих скриптов проходят; локальный запуск скрипта в режиме чтения на каждом слитом Pull Request из диапазона #15–#46 не срабатывает по правилу 1, а каждое срабатывание правил 2 и 3 разобрано по diff и приведено в описании Pull Request; на Pull Request этого изменения успешно завершаются `commitlint` и `verify`.

Вне рамок: включение `test-integrity` в обязательные status checks и любые настройки репозитория и ruleset (отдельный шаг владельца после слияния); механизм одобрения внутри проверки; разбор кода тестов синтаксическим анализатором; обнаружение ослабленных утверждений, обновлённых снапшотов и удобных моков; изменение кода приложения и существующих тестов.

Зависимости: встроенные `fetch` и `node:test` из Node 22, автоматический `GITHUB_TOKEN` с правами `contents: read` и `pull-requests: read`; новых npm-зависимостей и секретов нет.

Риски:

- Подсчёт текстовый, а не синтаксический: маркер или вызов `it(` внутри строки или комментария учитывается. Возможны ложные срабатывания и пропуски; формы вне списка (например, `test.fixme(` в Playwright или `it.skip.each`) правилом 2 не ловятся.
- Условный пропуск в новом тестовом файле (`test.skip(condition, reason)` в Playwright) считается маркером и роняет проверку. Это осознанная цена простого правила: такой Pull Request сливает владелец.
- Сумма в правиле 3 позволяет перенести тест-кейсы между существующими файлами, но так же позволяет скрыть удаление кейсов в одном файле добавлением в другой изменённый существующий файл.
- Проверка не останавливает агента с правами администратора: обход ruleset доступен ему так же, как владельцу. Проверка создаёт осознанное трение, а не техническую границу.
- На Pull Request этого изменения job `test-integrity` не запускается: `pull_request_target` использует workflow базовой ветки, где этого job ещё нет. Существующая проверка `protected-paths` на нём ожидаемо падает, потому что изменение затрагивает `.github/**`; владелец сливает его через обход ruleset `Protect main` после подтверждения зелёных `verify` и `commitlint`.
- Имя проверки `test-integrity` позже станет обязательным status check, поэтому переименование job после этого потребует синхронного изменения настроек репозитория.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None. Наблюдаемое поведение приложения не меняется, поэтому изменение объявлено с `skip_specs: true` без spec delta.

## Impact

Затрагиваются только CI-конфигурация (`.github/workflows/protected-paths.yml`, `.github/scripts/test-integrity.mjs` и его тесты) и по одному абзацу в `docs/engineering/protected-operations.md` и `docs/engineering/agent-workflow.md`. Скрипт `protected-paths.mjs` и его тесты не меняются: несколько строк работы с API продублированы в новом скрипте вместо выноса в общий модуль. Код приложения, существующие тесты, схема базы данных, зависимости, секреты и настройки репозитория не меняются. Документ `design.md` не создаётся: правила, список маркеров и модель запуска определены владельцем и изложены выше.
