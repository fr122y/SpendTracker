# Proposal

## Why

По коммиту нельзя узнать, к какому изменению OpenSpec он относится. Из последних 40 коммитов в `main` ни один не содержит трейлер `Change:`; в ai-harness, где то же правило записано, но проверяется лишь частично, его содержат 17 из 40. Без трейлера цепочка `git blame` → коммит → proposal, design и tasks обрывается на коммите, а после архивации папки изменения коммиты этого изменения нельзя найти и по путям. Правило, записанное только в документации, не соблюдается, поэтому его проверяемая часть должна стать проверкой слияния.

## What Changes

- Записать правило в `docs/engineering/change-request.md` (новый раздел «Trailers»): коммит, который реализует, продолжает, исправляет или архивирует работу изменения OpenSpec, содержит трейлер `Change: <change-id>`, где `<change-id>` — имя папки изменения в `openspec/changes/` (для архивного — без префикса даты `YYYY-MM-DD-`); коммит, работа которого относится к задаче из реестра задач владельца, содержит `Refs: <task-id>`. Трейлеры стоят в последнем блоке сообщения коммита, а не только в описании Pull Request: тело squash-коммита GitHub собирает из сообщений коммитов (`squash_merge_commit_message: COMMIT_MESSAGES`), и описание Pull Request в историю `main` не попадает.
- Исправить в том же документе раздел «Squash Commit Body»: тело squash-коммита пишется в сообщении коммита, а ссылки на задачу и изменение оформляются трейлерами.
- Добавить по одной строке в `AGENTS.md` (раздел «OpenSpec» и указатель на руководство), в шаги реализации и архивации раздела «OpenSpec Changes» в `docs/engineering/agent-workflow.md` и в раздел «References» шаблона `.github/pull_request_template.md`.
- Добавить в workflow `.github/workflows/protected-paths.yml` третий job `change-trailer` на том же событии `pull_request_target`: workflow и скрипт берутся из базовой ветки, код из head Pull Request не извлекается и не исполняется, списки файлов и коммитов читаются только через REST API. Два существующих job не меняются.
- Добавить скрипт без зависимостей `.github/scripts/change-trailer.mjs`. Из изменённых файлов Pull Request (поля `filename` и `previous_filename`) собирается множество затронутых изменений: путь `openspec/changes/<id>/…` даёт `<id>` (кроме буквального `archive`), путь `openspec/changes/archive/<dir>/…` даёт `<dir>` без ведущей даты. Из сообщений всех коммитов Pull Request собираются строки вида `^Change:\s*(\S+)\s*$`; ключ чувствителен к регистру, идентификаторы сравниваются точно.
- Проверка проходит, если каждое затронутое изменение названо в трейлере хотя бы одного коммита. Лишние трейлеры с идентификаторами изменений, папки которых Pull Request не трогает, разрешены: так оформляются последующие исправления. Pull Request, не затрагивающий ни одной папки изменения, проходит.
- При нарушении проверка завершается с кодом 1 и перечисляет каждое изменение без трейлера, точную строку `Change: <id>` и то, что она должна стоять в сообщении коммита; то же простым языком пишется в `$GITHUB_STEP_SUMMARY`. Собственного механизма обхода нет: исправление — ещё один коммит с трейлером, достаточно пустого (`git commit --allow-empty`).
- Проверка закрывается в безопасную сторону с кодом 2: ошибка API, сдвинувшийся head, неполный список файлов или коммитов, список коммитов без head-коммита. API отдаёт не более 250 коммитов одного Pull Request; если их больше, проверка завершается с ошибкой и сообщением об этом пределе.
- Добавить unit-тесты `.github/scripts/change-trailer.test.mjs`; job запускает их перед самой проверкой.

Критерии приёмки: unit-тесты всех трёх скриптов проходят; локальный запуск скрипта в режиме чтения на слитых Pull Request #41, #42, #44, #46, #49 и #53 даёт провал (они созданы до правила), на слитом Pull Request без папок OpenSpec — успех, на Pull Request этого изменения — успех с идентификатором `add-change-trailer-check`; на Pull Request этого изменения успешно завершаются `verify`, `commitlint` и `test-integrity`.

Вне рамок: проверка `Refs:` (существование задачи в реестре владельца из репозитория определить нельзя); обнаружение коммитов, которые относятся к изменению, но не трогают его папку; требование, чтобы строка `Change:` стояла именно в последнем блоке трейлеров; включение `change-trailer` в обязательные status checks и любые настройки репозитория и ruleset (отдельный шаг владельца после слияния); исправление уже слитых коммитов (`main` запрещает переписывание истории); переход на ветки `agent/<change-id>` — имена веток остаются `task/…`; изменение кода приложения и тестов.

Зависимости: встроенные `fetch` и `node:test` из Node 22, автоматический `GITHUB_TOKEN` с правами `contents: read` и `pull-requests: read`; новых npm-зависимостей и секретов нет.

Риски:

- Проверка требует трейлер только для изменений, папки которых затронуты. Pull Request с кодом изменения, но без правок в его папке, пройдёт без трейлера; эту часть правила держит только документация.
- Достаточно одного коммита с трейлером на весь Pull Request. При squash-слиянии этого хватает, потому что в `main` попадает один коммит с телом из всех сообщений.
- Строка `Change:` учитывается в любом месте сообщения коммита, а не только в последнем блоке: в теле squash-коммита блоки трейлеров исходных коммитов оказываются в середине.
- Проверка проверяет наличие связи, а не её правильность: трейлер может назвать изменение, к которому коммит по смыслу не относится.
- Проверка не останавливает агента с правами администратора: обход ruleset доступен ему так же, как владельцу. Проверка создаёт осознанное трение, а не техническую границу.
- На Pull Request этого изменения job `change-trailer` не запускается: `pull_request_target` использует workflow базовой ветки, где этого job ещё нет. Существующая проверка `protected-paths` на нём ожидаемо падает, потому что изменение затрагивает `.github/**`; владелец сливает его через обход ruleset `Protect main` после подтверждения зелёных `verify`, `commitlint` и `test-integrity`.
- Имя проверки `change-trailer` позже станет обязательным status check, поэтому переименование job после этого потребует синхронного изменения настроек репозитория.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None. Наблюдаемое поведение приложения не меняется, поэтому изменение объявлено с `skip_specs: true` без spec delta.

## Impact

Затрагиваются CI-конфигурация (`.github/workflows/protected-paths.yml`, `.github/scripts/change-trailer.mjs` и его тесты, одна строка в `.github/pull_request_template.md`) и документация (`docs/engineering/change-request.md`, `docs/engineering/agent-workflow.md`, `AGENTS.md`). Скрипты `protected-paths.mjs` и `test-integrity.mjs` и их тесты не меняются: несколько строк работы с API продублированы в новом скрипте вместо выноса в общий модуль. Код приложения, существующие тесты, схема базы данных, зависимости, секреты и настройки репозитория не меняются. Документ `design.md` не создаётся: правило, логика проверки и модель запуска определены владельцем и изложены выше.
